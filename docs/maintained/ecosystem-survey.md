# 生态调研：对标项目、AstrBot 痛点、我们的差异化

> 2026-10-23。用户在 NapCat 项目下看到机器人推荐列表（点名 **MaiBot**），
> 要求调研"别人做到什么程度 + AstrBot 插件市场痛点"，前提是**不重复造轮子**。
> 本文是调研结论，**不含实现**；要做的项另行排期。

## 1. 对标：MaiBot（麦麦 / MaiSaka）

| 项 | 数据 |
|---|---|
| Stars | 6.3k–6.4k（2026-10 仍活跃，v1.3.11） |
| 许可 | GPL-3.0 + EULA |
| 技术 | Python 3.10+，MaiCore(FastAPI) + 适配器(WebSocket) + WebUI，主要跑 QQ/NapCat |

**设计原则（最重要的一句）**：「**最像，而不是最好**」——
不是"什么都能解决的 helpful assistant"，而是"会犯错、有自己想法和感受的生命"。

### 1.1 它的能力清单

1. 自然对话风格：长短不一的闲谈，拒绝 markdown 式长篇回答
2. 智能发言时机：读气氛，该开口就开口、该沉默就沉默
3. 社交学习：模仿群友说话风格，自动挖掘群里黑话并在合适场景用出来
4. 记忆分层：短期（窗口+压缩，约 5× 上下文扩展）／中期（聊天回想）／
   长期（LPMM，建在 HippoRAG 2 上，含知识图谱与 ReAct 检索）
5. 人物画像：亲密度分数、对每个群社区文化的印象
6. 插件 + 事件系统、WebUI（配置热重载、记忆可视化、插件市场）

### 1.2 发言时机怎么做的（细节最值得抄）

- **HeartFlow 心流**：每个群一个 SubHeartflow，持续"看"群里在聊什么，不是请求-响应
- **Willingness（回复意愿值）**，这是它的核心节奏控制器：
  - 收到消息 → 按消息特征算意愿分
  - **开始思考 → 意愿 −2.0**（防止连续快速回多条）
  - **发出去后 → 意愿 +0.2**（小幅回升，允许有限跟进）
  - 随时间自然衰减
  - 响应概率 = `(willingness − 阈值) × 2`
- **退避**：连续决定不回复后放慢检查（`no_action_backoff`：2 次后开始，15s 起步，300s 封顶）
- **按时段/按群调频率**：`talk_value_rules`（如 00:00-08:59 → 0.8，09:00-18:59 → 1.0）
- **防抖**：`message_debounce_mode = off / fast / natural / steady`
- **消息过滤**：`ban_words`、`ban_msgs_regex`、单条图片数阈值

### 1.3 拟人细节（形态层）

会**故意打错字、连发好几条碎片消息、大小写不一致**——就是不想让你觉得它是机器人。
架构上「**想什么**」和「**怎么说**」是分开的，所以调人格风格不用动推理逻辑。

> ⚠️ 最后一点和我们已经做的「判定 / 生成分离」是同一个思路，说明路线是对的。

## 2. 对标：NapCat 生态的其他项目

| 项目 | 定位 |
|---|---|
| **NoneBot2** | Python 通用框架，AI 靠插件拼装 |
| **Lighthouse** | 基于 NapCat 的 Python 框架，对"接大模型"较顺手 |
| **Koishi** | TypeScript，通用生态广，AI 非核心 |
| **AstrBot** | **AI 是一等公民**，多平台 + 插件市场 |
| go-cqhttp | **已停更**，不建议新用 |

一篇工程实践文章（nbility.dev）的共识，和我们踩过的坑高度一致：

- **别把整个群聊喂给模型**：消息分三类——显式触发 / 低成本记录 / 忽略
  （表情、刷屏、过短、重复、机器人自己的消息）
- **成本是硬约束**：每条都送大模型会烧钱
- 权限、日志（403、断连、模型错、图片投递失败）必须可追溯

## 3. AstrBot 生态的痛点（多家第三方评测一致指出）

| 痛点 | 说明 |
|---|---|
| **插件质量参差** | "1000+ 插件是生态幻觉的开始"，社区插件**无统一 review**，引入来路不明的插件等于增加攻击面 |
| **插件兼容性脆弱** | AstrBot 周更（v4.27.2/3/4 一周内），但**没有插件 API 的语义化版本策略**，插件可能升级后静默失效 |
| **拟人化不是强项** | 评测原话："更擅长群聊和专业工具场景，**在拟人化私聊体验上不如专注情感陪伴的项目**" |
| 运维与成本 | 自托管无 SLA；成本随模型调用线性增长 |
| 其他 | AGPL 商业风险、微信个人号封号风险、文档中文优先 |

## 5. 建议（按优先级）

1. **回复意愿值（willingness）** —— 最高价值。**已实现**（插件侧，默认关闭）。我们现在是"每条独立判定 + 硬限流"，
   没有"刚说完就降欲、随时间回升"的节奏，所以可能出现"连着说两句"这种不像人的情况。
   MaiBot 的 −2.0 / +0.2 / 衰减 这套很成熟，直接借鉴，落进影子插件（不碰 core）。
### 5.1 意愿值：对照实验（已验证）

同一批场景，只切换 `willingness_enabled`：

| | 结果 |
|---|---|
| 关闭 | 3 个场景**连续 REPLY 三次** —— 连说三句，不像人 |
| 开启 | 第 1 次 REPLY，后 2 次压为 SKIP，理由「刚说完，回复意愿 0.21 低于阈值 0.45，先闭嘴一会」 |

参数（都可调）：`willingness_base=1.0`、`drop=2.0`、`recover=0.2`、
`recover_per_minute=0.3`、`threshold=0.45`、`amplifier=2.0`。
**默认关闭**，所以不影响正在收集的真实数据；用户醒了再决定要不要开。

2. **按时段 / 按群的频率规则** —— `max_per_hour` 是全局的，凌晨和白天、
   技术群和闲聊群该不一样。配置驱动，改动小。
3. **"连续不回复"退避** —— **已实现**（默认关闭）。决定不说话时不用每条都问模型，`no_action_backoff` 那套，
   直接省 token。
### 5.2 配额与退避：怎么用（都已实现，默认不生效）

```jsonc
// 插件配置 astrbot_plugin_proactive_shadow_config.json
"max_per_hour": 60,                    // 兜底配额，0 = 不限
"hourly_quota_rules": [                // 按时段覆盖（支持跨夜，如 23:00-02:00）
  { "hours": "00:00-08:59", "max_per_hour": 20 },
  { "hours": "*",          "max_per_hour": 60 }
],
"group_quota": { "827767299": 40 },    // 按群覆盖，优先级最高
"no_reply_backoff_enabled": false,     // 连续沉默后退避（默认关）
"backoff_start_count": 2,
"backoff_base_sec": 15,
"backoff_cap_sec": 300
```

优先级：**按群 > 按时段 > `max_per_hour`**。三者都是 0/空 = 不限，
所以不配置时行为与改动前完全一致。

⚠️ 退避**默认关闭**是有意的：它只在"连续判定为不说话"时触发，而 REPLY 率才 4%，
开着会把大部分判定都省掉 —— 那正是我们**现在还在收集数据**的阶段最不想要的。
等数据够了、正式上线时再开。

4. **形态层拟人** —— 碎片消息、偶尔错字。**但必须先确认 splitter 会不会重复分段**，
   否则两个插件一起切，反而乱。

## 6. 明确不做（防重复 / 防跑偏）

- ❌ 不自己做记忆系统（livingmemory 在做）
- ❌ 不自己做人格演化或黑话挖掘（self_learning 在做）
- ❌ 不自己做分段（splitter 在做）
- ❌ **不全盘照抄 MaiBot**：它是"陪伴型数字生命"，明确**不为完成任务设计**；
  我们的群是技术群，用户要的是「**有信息量 + 时机对**」。
  学它的**节奏控制**，不学它的"故意犯错/卖萌"。
- ❌ 不做插件市场/分发（AstrBot 已有）

### 7.1 诚实边界：形态层的研究还不够细

调研里我只摸到 MaiBot 形态层的**结论**（"会故意打错字、连发好几条碎片消息、
大小写不一致"），**没有展开研究它具体怎么做**——
比如错字是生成时注入还是后处理、碎片怎么切分、频率怎么控制、会不会让人觉得敷衍。

所以形态层如果要做，**需要先补一轮针对性调研**，不能照着一句话就实现。

### 7.2 S9-6 的建议顺序

1. **引用**（数据指向最明确：37.5% 的 REPLY 判定需要引用，发送端完全没实现）
2. **消息过滤**（MaiBot 有、我们没有；实现小、收益直接——省掉垃圾消息的判定开销）
3. **形态层**（先补调研，再实现；且必须先确认 splitter 会不会重复分段）
