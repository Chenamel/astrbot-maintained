# 维护保护与执行授权 · 业务全景

## 1. 为什么有这两条链路

它们解决的是两个"自保"问题：

| 问题 | 不解决的后果 |
|---|---|
| **补丁被覆盖** | 启动器/插件市场一更新，手工维护的补丁全没了 → 插件 import 不到 core 私有符号 → **整个插件加载失败**（本项目立项的直接起因） |
| **执行类操作被误触发** | 模型在非授权语境下调用 shell/python，等于把机器交出去 |

## 2. 术语

| 术语 | 含义 |
|---|---|
| **维护名单（maintenance registry）** | `data/optimization_tracking/maintenance_registry.json` 的 `protected_plugins` 数组 |
| **维护保护** | 命中名单的插件在更新/覆盖安装前被**抛错阻断** |
| **执行授权（execution denial）** | 判定"当前这条消息是否**真的**授权了执行类操作" |
| **双通道匹配** | 名单同时匹配插件的注册名 `name` 与安装目录名 `root_dir_name`（覆盖"目录改名"场景） |

## 3. 能力地图

```
自保
 ├── 维护保护        → 名单内插件在 4 条进程内更新路径上被拦截
 └── 执行授权        → 只有"管理员 + 消息里明确说跑"才允许执行 shell/python
```

## 4. 端到端流程（用户/运维视角）

**维护保护**
1. 运维把某插件写进 `maintenance_registry.json` 的 `protected_plugins`
2. 用户在 Dashboard 点"更新插件" → 命中名单 → 抛 `LocalMaintenanceProtectionError`
3. Dashboard 单个更新：转为 `PluginServiceError`，前端弹明确报错
4. Dashboard 批量更新：该插件状态记为 **`skipped`**（跳过而非失败），其余插件照常更新，末尾提示"已跳过 N 个本地维护插件"

**执行授权**
1. 用户（管理员）说"帮我跑一下这段代码" → 命中执行授权 → shell/python 工具可用
2. 用户（管理员）说"解释一下这段代码" → **不授权** → 请求装配阶段就把执行类工具摘掉
3. 非管理员：无论怎么说都不授权

## 5. 通用规则与边界

| 规则 | 说明 |
|---|---|
| 保护**双向通道** | 插件名或目录名任一命中即拦截 |
| registry **存在但损坏 → 拒绝**（fail-closed） | 缺 key / 非 list / 元素非 str / JSON 坏 → 抛错 |
| registry **文件缺失 → 放行**（fail-open） | ⚠️ 删掉文件即可绕过全部保护 |
| 保护**只管更新** | `uninstall_plugin` / `install_plugin` / `install_plugin_from_file` **未挂闸门** → 可"先卸载再安装"绕过 |
| 授权 = **管理员身份 + 明确祈使语句** | 两道都过才放行 |
| 授权判定**只看本条消息正文** | 排除 `Reply` 引用内容、剔除代码块/行内 code/引用行后分句判定 |
| 摘工具发生在**请求装配期** | 比工具边界更早（双保险） |

## 6. 明确不做什么

- **拦不住启动器**：无文件锁、无目录监听、无哈希校验。README 自认此局限。
- 不做文件系统级权限隔离（闸的是工具调用入口，不是 OS 权限）。
- 不做"持久 shell 会话的后续调用再鉴权"（授权只看会话创建/操作时那条消息）。
- 不做内容安全（那是另一个插件的事，本 fork 不含）。
