# 长期记忆插件入库 vs 内容安全审计的顺序观察（P? 观察项 · T8-09）

> **结论先行**：实例里的长期记忆插件，其「反射入库」**没有早于**内容安全审计。
> 因此**本 fork 不需要为此做任何改动**，本轮只出结论、不写 core 代码。
> 调查时间：2026-10-12。方式：静态代码追踪（core 侧机制）+ 实例插件配置实测。

## 1. 待验证的假设

> "记忆插件在 `on_llm_response` 里把助手回复写进记忆库，这一步可能早于内容安全插件的审计，
> 于是未审计文本被持久化。"

验证方式：确认**同一事件上两个钩子的先后顺序**，以及**审计是否原地改写同一个响应对象**。

## 2. 结论：假设不成立

| # | 证据 | 出处 |
|---|---|---|
| 1 | 事件钩子按 `priority` **降序**执行（数值越大越先），缺省 `0` | `astrbot/core/star/star_handler.py:26` |
| 2 | 内容安全插件的响应钩子 `priority=1000`；记忆插件的响应钩子**缺省 0** | 实例插件各自 `main.py` |
| 3 | 审计未通过时，审计插件**原地改写同一个 `LLMResponse`**：`completion_text=` / `raw_completion=None` / `reasoning_content=None` | 实例插件 `_replace_response()` |
| 4 | 反射读取的正是 `resp.completion_text` ⇒ 拿到的是**审计后 / 重试后 / 拦截话术**文本 | 实例插件 `memory_reflection` |
| 5 | `OnLLMResponseEvent` 的**唯一派发点**是先于 `OnAgentDoneEvent` 的那一行，且主对话默认挂载该 hooks | `astrbot/core/astr_agent_hooks.py:33`、`astrbot/core/astr_main_agent.py:1875` |
| 6 | 审计拦截会 `event.stop_event()`；事件钩子循环在每个 handler 之后检查 `is_stopped()` ⇒ **后续 handler 不再执行**，被拦内容不入库 | `astrbot/core/pipeline/context_utils.py:131` |
| 7 | 审计重试走的是直连 provider 的 LLM 调用接口，**不派发任何事件钩子** ⇒ 重试期间的中间被拒文本不会二次触发反射 | `astrbot/core/star/context.py:171` |

⇒ **在审计生效的场景下，入库文本一定是审计后文本。**

## 3. 真实风险不在"时序"，而在"覆盖不到"

实测实例配置后，审计插件的真实生效面比想象中窄：

| 盲区 | 成因 | 影响 |
|---|---|---|
| **私聊完全不审计** | 响应钩子开头：`group_only` 为真时对私聊直接 `return` | 私聊的助手回复零审计即入库 |
| **用户输入侧完全不审计** | 输入检查开关关闭；且记忆插件用自定义过滤器**被动捕获**群消息（过滤器恒不通过 ⇒ 不唤醒 AstrBot） | 群里的用户发言零审计即入库 |
| **输出侧实际只有一道闸** | 白名单 / 黑名单 / 关键词 / 重复回复拦截四项开关**全部关闭**，只剩「LLM 审查 + 1 次重试」 | 群聊输出侧只有单层 LLM 审查 |

注：用户发言未经审计即入库，是长期记忆插件的**设计本意**（要记住用户说过什么）——
是否算问题，取决于对"记忆库内容"的定性，不由 core 决定。

## 4. 附带发现（**仅记录，本轮不修**）

| 项 | 说明 | 为何暂不构成问题 |
|---|---|---|
| 反射钩子**没有** `is_chunk` 判断 | 审计插件有 `if response.is_chunk: return`，记忆插件没有 | 当前 `OnLLMResponseEvent` 只有一处派发，且传入的是最终聚合响应（非流式分片），因此不会逐片入库。若将来出现"流式分片也派发该事件"的路径，需要给记忆插件补这个判断 |

## 5. 处置建议

1. **core 不动**：全部结论落在插件配置与插件自身范畴；按六铁律第 1 条，这不是 `astrbot/api/**` 的职责，也不该改 core 去迁就某个第三方插件。
2. 若要收紧，优先级建议：① 关掉 `group_only` 或改为按场景放行 ⇒ 让私聊也进入输出审计；
   ② 若要审计"入库前的用户发言"，应在记忆插件侧加可选的输入审计开关。
3. 两条都属**插件侧**动作，与本 fork 无关，本轮不做。

## 6. 方法备注

- 判定钩子顺序**不能靠猜测**：必须回到 `star_handler.py` 的排序实现确认方向（降序 / 缺省值）。
- "审计是否生效"要看**实例实际配置**，不能只看代码默认值 —— 本次四项开关全关就是靠读配置才发现的。
